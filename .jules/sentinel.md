# Sentinel Security Journal

## 2026-07-12 - Hardening M-Pesa Edge Function and Payment Validation
**Vulnerability:** Unauthenticated/unauthorized API trigger and price tampering in payment Edge Functions. The M-Pesa STK push function did not verify the user's JWT or authenticate requests, allowing any anonymous caller to request payments. Additionally, it accepted the transaction amount directly from the client request payload (`amount`), allowing malicious checkout clients to manipulate the actual price of an order. It also leaked full error stack details/strings to the client-facing responses in the catch block.
**Learning:** Deno-based Supabase Edge Functions must always explicitly parse and verify the user's JSON Web Token (JWT) from the HTTP `Authorization` header to determine user identity and permissions. Crucially, checkout total amounts must be verified directly against the single source of truth (the database `orders` table using a service role client to bypass user RLS constraints) rather than trusting client-sent payloads. Furthermore, server-side failures must be securely generic (e.g. `"Internal Server Error"`) to avoid leaking implementation details.
**Prevention:** Always include a case-insensitive `Authorization` header check, extract the token using `.replace(/^Bearer /i, "").trim()`, and verify with `supabase.auth.getUser(token)`. When performing payments, load the order details directly from the DB by `id` using `SUPABASE_SERVICE_ROLE_KEY` and verify that the calling user matches the order's `buyer_id` and that the order is `'pending'`. Always log verbose errors on the server (`console.error`) while returning a generic response message to client-facing requests.
